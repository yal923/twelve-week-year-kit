# 最小能力验证 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 建议由当前协作 Agent 顺序执行；执行方式与测试范围须由各自账号持有人确认。本清单保持可复用，单次批准和结果另见 STATUS 与运行报告，不从未勾选框推断未执行或从他人的完成推断本侧获准。

**Goal:** 用有边界的虚构试验，取得两台 Mac 上共同工具运行及 Notion 自动读写的直接证据，识别工程阻断。

**Architecture:** 各宿主独立执行同一清单，使用本人指定的空白测试根和产品目录外的私有日志。先验证本地工具和连接，再用两个简化库测试关系、公式、视图与恢复所需读回；不建设完整安装器。

**Tech Stack:** 已有宿主、已有 Notion 连接、macOS 已有的 `/bin/sh` 与基础命令；不安装依赖。本地样例只证明进程／文件能力，不决定产品最终采用 Shell、Node 或 Python。

**Spec:** [工程设计 review.4](../../specs/notion-build-spec.md) §3–§8、[数据约定](../../data-contract.md) §7、[架构](../../architecture.md) §5；本计划为 U01／U07 收集部分证据，不等于 A01–A25 产品验收。

**设计基线:** `a78649ab880e3cccbb188a5bb225453b325b6df0`；执行时若规格已变，先核对差异是否影响本计划，不默认沿用旧授权范围。

## 批准时所需输入与修改范围

批准内容是这份计划及其固定试验范围。所有者提供一个自己 Notion 中的空白测试页 URL，并确认该页用于本次验证；Agent 读取连接身份及目标页，确认匹配后才能写。若所有者只指定上层位置而要求代建测试根，先补充一次建根动作及其身份标记／未知结果恢复方案，不能默认为已有授权。

私有目录默认建议放在产品包旁的 `twy-private/capability-checks/<run_id>/`，与 `twelve-week-year-kit/` 并列。批准该默认位置即可，无须用户自己建立文件或写程序；换位置时由本人指定。`run_id` 是本次随机 UUID，不取姓名或机器名。未提供 Notion 测试页时，可完成已获准的本地部分，停在 Notion 写入前。

| 范围 | 本次最多主动新增／修改 |
|---|---|
| Notion 测试根 | 2 个简化数据库、其中 4 条记录、根页面中的 1 个链接视图；平台自动附带的默认视图单独登记 |
| Notion 后续修改 | 将其中 1 条测试行动的 Week 从 2 改成 1，回读；不修改根页面标题、删除内容或更改其他记录 |
| 私有目录 | 本地样例、输入／输出、执行配置、操作日志、原始证据、映射与结论 |
| 产品仓库 | 批准和结果的文档记录；无完整产品工具代码。真实测试回执不进入公开仓库 |

临时探针文件职责：`probe.sh` 执行固定本地样例；`input.txt` 为虚构输入；`result.txt` 为结果；`run.json` 保存计划版本、宿主／环境、账号／根、授权引用及本次 ID；`operations.jsonl` 追加操作状态；`evidence/` 保存实际回执；`report.md` 总结能力。上述私有文件只有执行获准后才创建。

账号连接和宿主权限由账号持有人完成。当前 Agent 无法直接操作另一人的 Mac 或未连接账号；WorkBuddy 一侧须由那一侧会话读取本计划并取得本人对应授权，开发者批准不能替代她的账号授权。

## Task 1：核对环境并执行最小本地样例

**Files:** 执行后在获准私有目录创建 `run.json`、`probe.sh`、`input.txt`、`result.txt`、`report.md`。

**Interfaces:** 输入为批准记录和私有目录；输出为实际宿主／系统版本、文件与进程能力证据。没有得到版本时写 unknown，不猜版本。

- [ ] 记录宿主显示的版本；执行只读的 `uname -m` 和 `/usr/bin/sw_vers -productVersion`；仅检查命令位置与版本，不列环境变量、配置文件或凭证。
- [ ] 核对私有目录与产品目录不同，建立本次新目录；已有目录不覆盖，先按 run_id 判断是否为接续。
- [ ] 将以下完整样例写入本次 `probe.sh`，输入文件写三行 `2`、`3`、`5`。使用已批准路径作为唯一参数，不要求使用者输入命令。

```sh
#!/bin/sh
set -eu
probe_dir=${1:?approved probe directory required}
test -d "$probe_dir"
test -f "$probe_dir/input.txt"
actual=$(/usr/bin/awk '{ total += $1 } END { print total }' "$probe_dir/input.txt")
test "$actual" = 10
umask 077
if test -e "$probe_dir/result.txt"; then
    test "$(/bin/cat "$probe_dir/result.txt")" = "$actual"
else
    printf '%s\n' "$actual" > "$probe_dir/result.txt"
fi
test "$(/bin/cat "$probe_dir/result.txt")" = 10
printf 'local_probe_pass\n'
```

- [ ] 由宿主执行 `/bin/sh`，参数依次为本次 `probe.sh` 的绝对路径与私有目录的绝对路径。预期退出码 0、输出 `local_probe_pass`、结果文件为 `10`。
- [ ] 重复同一次调用，预期仍通过且结果文件未被重写；另用只读调用重新打开结果。保存命令退出码及原始结果，不把模型计算的 10 作为执行证据。
- [ ] 记录额外权限提示／人工操作。样例失败则保留具体错误，不改用用户手工配置来判通过。Shell 样例通过只关闭这一个探针项，U07 最终分发选择仍需两端证据。

## Task 3：执行固定的 Notion 小样例

**Files:** 私有日志、ID 映射、逐次请求／响应。Notion 对象限定为上表内容。

**Interfaces:** 消费 Task 2 的已核对身份、根、数据源和工具映射；产生实际字段、关联、公式值、视图配置和行集证据。

所有样例均是虚构测试数据，不是正式 Goal／Tactic 业务记录。首次创建数据库同时写入数据 §7.1 格式的标记，logical_key 分别为 Goals 与 Tactics；instance_id、operation_id 由本次预分配 UUID 绑定。记录首次创建同时携带 instance_id、record_id。每次创建前写回并读回 in_flight，每个对象单独创建，不依赖未验证批次原子性。

| 对象 | 固定定义／预期 |
|---|---|
| `TWY Probe Goals` | Name: title；instance_id、record_id: rich_text |
| `TWY Probe Tactics` | Name: title；instance_id、record_id: rich_text；Goal: 关联本次 Goals 数据源；Week、Order、ProbeValue: number；Double: formula，表达式 `prop("ProbeValue") * 2` |
| 目标记录 | Name=`虚构目标`，两个身份字段均为本次值 |
| 行动记录 W1B | Goal=本次目标记录；Week=1；Order=20；ProbeValue=1；Double 预期 2 |
| 行动记录 W1A | Goal=本次目标记录；Week=1；Order=10；ProbeValue=2；Double 预期 4 |
| 行动记录 W2C | Goal=本次目标记录；Week=2；Order=30；ProbeValue=3；Double 预期 6 |
| 根中的链接视图 | Name=`TWY Probe Week1`；源为本次 Tactics；table；Week=1；Order 升序；依次显示 Name、Goal、Week、ProbeValue、Double |

- [ ] 创建 Goals 库，首次请求包含 description 标记；直接读取返回的数据库及数据源，校验父位置、标记和字段。
- [ ] 使用实际返回的 Goals data source ID 创建 Tactics 库，首次携带标记及上表定义。Codex 的 schema 支持 `RELATION('实际数据源 ID')` 和 `FORMULA('prop("ProbeValue") * 2')`；实际 ID 必须从本次回读取得，不能使用文档虚构 ID。
- [ ] 读取两库 schema，再逐条创建上表 4 条记录。关系使用真实目标记录 ID，数字用数值；保存每条实际返回 ID，分别回读公式与关联。
- [ ] 在测试根建立链接视图。Codex 的 create_view 使用 parent_page_id、本次 data_source_id 和已读视图 DSL；配置语义严格为上表条件。若当前 DSL 不支持该语义，标失败／缺能力，不放宽筛选。
- [ ] 读取保存的 view 配置，核对字段次序、过滤和排序；查询实际视图，预期只返回 W1A、W1B，且按此顺序。
- [ ] 对相同视图采用 page_size=1 及返回游标逐页读取，预期无重复、无遗漏，合计仍为 W1A、W1B。若宿主忽略分页或不暴露游标，记录这一分支未验证，不据小结果集推断分页通过。
- [ ] 读取 W2C 最新状态后仅更新 Week 为 1，等待更新完成再回读；再次查询视图，预期 W1A、W1B、W2C，Double 仍为 4、2、6。保留此次修改及原值证据，不重建视图来冒充动态更新。
- [ ] 核对测试根及新库清单；主动新增对象应为 2 库、4 记录、1 链接视图，平台默认视图另列。保存成功和失败证据；不存在的结果不补造。
