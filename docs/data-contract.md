# 数据约定｜0.1.0-review.3

状态：设计候选，待审核。关联 R04–R19、R21。本文规定数据语义；字段中文显示名可以改变，含义和稳定键不能随宿主改变。

## 1. 所有权、身份与唯一来源

每次独立安装生成一个随机 `instance_id`，不从姓名、邮箱、机器名或 Notion ID 推导。所有记录有稳定随机 `record_id`，以及 `created_at`、`updated_at`、`revision`（从 1 递增，由 Agent 维护，见 §6）。关联用稳定记录 ID；适配层私下保存 Notion 页面／数据库／数据源 ID 映射，三者不得混用。尚未持久化的对话草稿不伪造 Notion ID／revision，恢复边界见引导协议 P01。

正式的个人记录、确认和修订保存在本人的 Notion 根页面及其子内容。本地私有文件只作连接映射、操作进度和可删除的只读快照。快照必须注明来源版本和导出时间，不接收编辑回写；同步、多主编辑和跨用户合并不在 v0.1 内。

通用证据标签：`user_reported`（本人陈述）、`user_confirmed`（本人确认）、`agent_candidate`（建议）、`unknown`（未知）。同一记录可以包含不同标签的字段；至少对愿景、目标、基线、完成报告和复盘结论标注来源。未知用空值加原因表达；不能用 0、空字符串或“未完成”冒充未知。

## 2. 逻辑记录与最低字段

| 记录 | 最低内容 | 关系和边界 |
|---|---|---|
| Profile / Vision | 当前处境、长期愿景、三年图景、限制／可用容量、时区、已确认与未知、引导阶段、下次问题、版本清单 | 每实例一个当前方向页面；允许各段分别为草稿，不强制愿景完整才开始 |
| Cycle | 名称、开始日期、时区、由日期推导的结束日期、状态、目标列表、确认时间、实际关闭时间／原因、前序周期 ID、方法／协议／数据版本 | 每实例 v0.1 最多一个 active；可以有多个历史 closed 和候选 draft；首周期无前序，后续引用本实例最近已关闭周期 |
| Goal | 名称、为什么值得做、结果判据、基线及来源、目标值／验收标准、单位、目标期限、观察频率、状态 | 恰属一个 Cycle；按确认时的愿景修订建立追溯引用；不是 Task |
| Tactic | 行动描述、作用假设、完成标准、执行周次集合、每周要求数量／单位、预计分钟、障碍与支持、版本、生效周 | 恰属一个 Goal；一次性行动的周次集合只有一个元素；v0.1 不多目标共用同一计分项 |
| WeeklyCommitment | 周次、Tactic 引用与版本、原始完成标准／数量／期限／预计用时快照、实际数量、完成证据及来源、完成时间、结算状态、是否基线项 | 每 Cycle + Tactic + 周次仅一个有效项；跨周不可复用同一记录 |
| ResultObservation | Goal、观察日期、实际值／质量验收、单位、证据或自评依据、来源、记录时间 | 独立于行动状态；缺数为未知，不从勾选数计算目标结果 |
| Review | 类型 weekly / cycle、Cycle、周次（周期复盘为空）、本周计划确认、基线承诺 ID 集合、结算版本历史、结果引用、解释假设、结构化决定集合、决定处置／观察记录、周期交接索引及接收处置、状态 | weekly 每周期每周一个；cycle 每周期一个，可在新周期草稿阶段承载接收处置；交接字段仅 cycle 使用，见 §2.2；同一周记录同时承载计划和复盘，结算历史见 §5.2 |

Profile 位于根页面，其他六类对应候选六库。共通元数据与关联作为属性；说明性文本和确认／修订记录可放正文。机器要读的基线、来源、操作记录须有固定标题和版本化结构，不依赖模型自由理解一大段聊天。实现阶段须给出具体字段类型和序列化格式，并保持这里的语义；不能任意增加必填用户输入。

“预计分钟”用于容量检查，不进入执行得分。实际分钟属于可选字段，不要求日常逐分钟计时。未来如果增加导出，必须保留 ID、关系、版本、证据标签和修订；CSV 展示副本不算完整可恢复备份。

### 2.1 复盘决定如何接回行动

决定存 Review 正文中的版本化结构化集合，无须新增数据库。每条最低包含：`decision_id`、`type`（keep/change/stop）、`target_refs`（本实例的 Goal／Tactic／Cycle ID）、`reason`、`proposed_change`、`confirmation`（候选或本人确认）、`effective`（明确 cycle_id + week，或 next_cycle_candidate）、`next_observation`（要观察的问题及 cycle_id + week／具体日期）。作用于容量或整周安排时引用 Cycle；不能只写无法定位的行动名称。

下一周计划确认前，必须列出已经本人确认、在本周生效或此前到期仍未处置的决定。每条追加处置记录：`decision_id`、目标周期／周、`adopted / not_adopted / deferred / superseded`、理由、确认来源、时间，以及采纳后对应记录的 ID／revision。adopted 必须在写入回读后成立；保留方案也要引用所保留版本。未采纳须本人确认理由；deferred 必填 `deferred_to`（新的 cycle_id + week 或 next_cycle_candidate），superseded 必填替代决定 ID。延后不算永久处理完：下次到期点取最新 deferred_to，否则取原 effective；到期的 deferred 和从未处置项都须重新列出。未处置不能默默越过本周确认。

新会话读取当前周期各 Review 的结构化决定集合及本周期接收的决定绑定（最多 12 个周记录加一个周期记录），不能只读最近一条而漏掉更早的决定；跨周期候选按 §2.2 从前序周期的 Cycle Review 交接索引恢复。字段读取在当前实例范围内进行，历史决定只按索引引用定位，不要求全文扫描个人历史。此读取和到期筛选能力属于必要的数据操作验收。

到达 next_observation 时，复盘列出到期或逾期尚未观察的决定，追加 `observed / unknown`、实际 Commitment／Observation 的引用、解释和下一步；缺失证据就保留 unknown。采纳进计划不代表实际执行或证明有效。跨周期候选仅在新周期本人选择后绑定真实 ID 和生效周，不提前创造任务。

### 2.2 跨周期决定的交接索引

Cycle Review 保存版本化 `handoff_index`：本 Cycle ID、生成时间、已核对的 Review ID／revision 集合、候选条目集合。每条保留原 `decision_id`、源 Review ID／revision、纳入原因、`carry / not_carried`、理由、本人确认及时间；继承项另引用上一周期接收处置版本。索引只引用决定，不复制第二份可编辑决定定义。空集合必须明确记录已完整核对，不能用空值冒充无候选。

周期关闭前，读取本周期全部 Review，包含本周期从前序接收条目的最新处置，列出全部已确认的 next_cycle_candidate、仍待采纳／延后中的决定，以及提前关闭后落在未运行周次的已确认决定。逐条确认 carry 或 not_carried；后者记录不再延续的理由，不改写过去的执行事实。已明确不采纳／已被替代的旧版本不再重复结转，替代后的未决决定仍须核对。读取不完整或有条目未处置时，保持 Cycle／Cycle Review 原状态，报告交接未完成；不能以未知分数可关闭为由跳过此检查。

新周期激活前，读取前序 Cycle Review 的最新索引，把每个 carry 条目的接收处置写入新周期的 Cycle Review：源索引版本、decision_id、`adopted / not_adopted / deferred`、理由、本人确认及时间。adopted 须绑定新周期真实 Goal／Tactic／Cycle ID、生效周、下次观察点和已回读的计划版本；旧目标／行动 ID 仅作来源，不作为新周期作用对象。该绑定进入 §2.1 的到期检查，原决定定义保留在来源处。not_adopted 需说明理由；deferred 须明确本周期具体周或 next_cycle_candidate，不能只写“以后”。延后至本周期某周的条目到期重新处置；再次延到下周期的条目必须进入本周期关闭时的交接索引，保留原 decision_id，不能在第二次交接时消失。

本周期没有前序时明确标记首次运行；有前序但索引缺失、不可读、版本已变而未重新核对，或 carry 条目尚无接收处置时，不激活新周期。已关闭周期之后订正交接内容须追加索引版本；已激活后发现源决定／索引变化时，保留新周期已确认计划，展示差异并重新处置，不自动改写承诺。采纳候选仍须通过正常目标与容量确认，不自动搬运旧任务。

## 3. 状态与激活条件

- Cycle：`draft → active → closed`。关闭不等于目标达成；可以本人决定提前关闭，保留名义 12 周边界及实际关闭时间／原因，不生成未运行各周的假记录。不能直接回开旧周期覆盖记录，订正走修订流程。
- Goal：`draft → committed → closed`。关闭时另填结果：`met / not_met / unknown`，不能从 Cycle closed 推导。
- Weekly Review：`draft → committed → settled`。周计划确认后为 committed；正式结算须周截止已过、所有基线承诺判定已知，否则保留 committed 和未结算摘要。已确认空周在周截止后可 settled，结果为 N/A。订正后的判定仍全部已知则保持 settled；订正导致 unknown 则退回 committed 并记录重开原因，保留旧结算版本，之后可以重新结算（§5.2）。Cycle Review：`draft → settled`，本人确认周期复盘后结案。周期关闭允许含未知的周，按 §5.1 展示记录覆盖，不能伪造补齐。
- Commitment 运行记录：`not_recorded / in_progress / reported_complete`；结算判定另为 `met / not_met / unknown`。取消、迟到是原因／事件，不能假装一种“自动免责完成”状态。

激活周期前，目标数量 1–3；每个目标有本人确认的最低投入理由；结果判据和期限清楚；基线已知或说明怎样／何时测量；关键行动有完整 12 周适用安排（允许先试再修）；容量已讨论；本人确认目标和承诺。探索目标的理由可以是“想了解哪种方式适合自己”，不要求已经知道长期愿景；AI 候选理由需本人认可后转为 user_confirmed。若连近期为何愿意投入也未知，则目标留 draft，不能仅靠确认“未知”激活。若某个指标基线未知到无法合理承诺数值，则先使用本人认可的测量／探索成果作为本周期目标，不能编一个目标值补齐。

周期关闭和新周期激活还必须完成 §2.2 的交接索引／接收处置检查；首次运行无前序的情况需明确记录。

本周确认前，只有属于当前周期的有效行动，日期在该周内，单位和要求清楚，总用时与可用容量核对。超容量时提出减少、延后或本人明确接受取舍，不能静默超排。若本周确实不承诺关键行动，可确认空周并说明原因，得分 N/A。

## 4. 周次、时间与计分单位

Cycle 开始日期由本人选定，保存 IANA 时区。第 n 周起始日 = 开始日 + 7 × (n−1) 个本地日历日；周起点和下一周起点都取对应本地日期的第一个有效瞬时，区间左闭右开。通常为零点；午夜跳变时取该日期首个存在的时刻，重复零点取较早瞬时。第 12 周最后日期为开始日 + 83 日。不能按固定秒数推导本地边界，不能借用 ISO 周号。v0.1 若所选周期遇到整日本地日期不存在的特殊历史时区变化，或宿主无法正确解析边界，须阻断该日期配置并说明，不悄悄挪日期。

开始日在周中也允许；第一周仍是七天。周期启动晚于开始日时，不生成已经过去的承诺或补记完成；先让本人决定保留原日期并记录未规划区间，或选新开始日。周期 active 后不直接修改开始日／时区来移动历史；确需调整须独立变更方案。

每个计分项是“某行动在某周的整体承诺”。例如每周练习 3 次，完成 2 次保留为 2/3，但该项计分为 0；达到 3 次且满足质量和期限才计 1。不是把练习 3 次拆成 3 分、另一项检查算 1 分。这是 D05 的产品选择，来源见 B06，不主张它对所有情形唯一正确。

每项的期限默认周截止，可提前至本周某日的截止。仅指定日期时，截止取次日本地日期的第一个有效瞬时（不含）；指定精确时间时以该瞬时为排他截止并在确认时说明，恰在截止发生属于逾期。日期边界与行动发生时间一律换算到 Cycle 的 IANA 时区后判定；设备时区和旅行地点不改变周期时区。

行动记录保留实际发生时间及其原时区／偏移或已明确的瞬时。含歧义的重复本地时刻须确认偏移；不存在的时刻或缺少时区、日期粒度不足以判定精确期限时，追问或保留 unknown，不猜测转换。本人明确确认发生在某个周期本地日期且足以判断日期期限时，可以使用该日期，不强制精确到分钟。补录时间只用于审计。

“第 13 周”只表示周期后的总结／恢复／准备时间，不是第 13 个计分周；旧周期不创建 week=13 的 Commitment 或 Weekly Review。补做原行动追加到原 Commitment 的逾期记录，保留实际日期且不提高原周得分；之后的结果仍可作为原 Goal 的带日期 Observation，必须标注在目标期限内或期限后。没有原行动的额外成果可进入 Cycle Review，不制造补记承诺；新周期若已开始，则新的承诺归属新周期，不能与旧周期重复记分。

## 5. 基线与评分规则

确认周计划时，在 Review 保存已确认的基线项 ID、判据与计分规则版本；每项保存同一份原始承诺快照。**这是可审计记录，不是声称 Notion 提供不可篡改存储。** Agent 发现两处不一致、已有来源被改或版本不连续，应先解决冲突再结算。

设 N = 基线项数量，D = 其中按时满足全部标准的项数，U = 仍无法判定的项数。以下正式结算适用于周截止已过；周内只显示当前进度与剩余时间，不提前发布最终得分。提前关闭周期时也不移动本周原边界；保留当前周的进度／未结算状态，后续可按原期限与真实事实补结算。

| 情况 | 展示与处理 |
|---|---|
| N = 0 | N/A（本周无关键行动承诺）；不显示 0% 或 100% |
| N > 0 且 U > 0 | 未结算；显示 D/N 和 U 项待确认，**不发布正式百分比** |
| N > 0 且 U = 0 | 正式得分 D/N × 100%；显示分子／分母和一位小数，按十进制四舍五入（half-up），例如 1/16 = 6.25% 显示 6.3%，不是 6.2%。85% 仅作作者经验参考 |
| 部分完成 | 实际数量保留，整体未达标计 0；不自行插入部分分 |
| 确认后新增 | 标记额外行动，保留价值与结果，不加进原基线分子或分母 |
| 确认后取消 | 保留原项与原因，若未完成为 not_met；未来周可以移除该行动。评分不作人格评价 |
| 确认后改标准／数量／排期 | 保存操作安排的新版本和变更理由；本周原基线继续可见、按原标准计；未来周按新版本 |
| 逾期完成 | 原周按原期限判定，另记实际完成；若本人重新承诺下一周，建立新项并引用前项，不自动搬迁 |
| 真实记录订正 | 本人确认订正事实与证据后追加前值、后值、原因、确认时间；允许出修订分数，保留原结算版本。不能用“订正”掩盖计划变更 |

v0.1 不做跨周平均分、跨目标加权总分或排行榜，避免把不同单位和缺失覆盖压成单一数字。结果变化、额外行动和执行分数并列解释。

结算时如果本人说“没记，想不起来”，保持 unknown；如果说“这一项没做”，才是已知 not_met。计划外达成目标仍是结果达成；行动全部完成而目标未达成仍须分别保存。

### 5.1 周期记录覆盖

这是资料完整程度，不是执行得分。每次报告保存 as_of；统计截止为 as_of 与实际关闭时间中较早者。纳入名义 12 周中起点早于该截止的周（可含已开始但未结束周）。完整结束纳入 12 周；提前关闭不将尚未开始的周算作缺口。

- H：已确认基线 N>0 的周数；S：其中最新结算有效、U=0 且已过周截止的 settled 周数。并列展示“已结算 S / 有承诺 H”。
- B：上述 H 周的基线项总数；K：这些项中已有 met／not_met 判定的项数，即 Σ(N−U)。展示“已知判定 K / 基线项 B”；不计额外行动、不去掉取消项、不转成综合百分比。
- E：已确认 N=0 的空周数，单列 N/A，不进入 H 或 B。
- G：纳入范围中没有确认周计划的周数，单列“未规划／缺记录”，不当作空周；尚未开始的周数另外注明，不充当缺失。

应满足 H+E+G = 纳入周数。0/0 显示为“无承诺周／无基线项，N/A”，不能视为 100% 覆盖。部分周未结束会使 S<H，不直接解释为漏记；同时注明仍在进行的周。若数据不可读或结构损坏，明确说明无法完整计算，列出不可读周；不能代入 0 或藏到 G。订正历史后按最新版本重算并保留此前报告版本。

虚构例：12 周中 11 周各有 2 项，W3／W7 各有 1 项 unknown，其余 9 周已结算；W9 是本人确认的空周。报告为 S/H=9/11、K/B=20/22、E=1、G=0、尚未开始=0，不写成 9/12，也不把 W9 算成失败。

### 5.2 结算与订正历史

每次首次结算或事实订正都在所属 Review 追加不可静默覆盖的结算快照：`settlement_id`、所对应 Review revision、前一 settlement_id、D/N/U、计分规则版本、基线与实际判定的记录版本引用、`scored / na / unsettled`、原因、确认来源／时间。原结算版本即这组历史快照；最新摘要引用最新一条，不覆盖旧条。未结算快照不含正式百分比。

已知事实订正使 1/2 变成 2/2 时，Review revision 递增、状态仍 settled，两次分数及依据均可读。如果证据撤回使 U>0，追加 unsettled 快照、退回 committed，当前摘要撤下正式得分；旧得分只作为被取代的历史显示。后续确认再追加新结算。周期复盘的覆盖和结果摘要被订正影响时，须追加修订版，不默默留下过时汇总。

## 6. 版本、修订与并发

变更记录最低为：记录 ID、前后 revision、变更字段的前后值、原因、提出者／确认来源、记录时间、生效周。可以作为所属页面的结构化追加段落，无须第七个数据库。

Agent 每次写前读取最新 revision、关键字段与平台更新时间，和生成方案时对比；有变化先合并讨论或重新生成动作清单。平台不保证条件写入时，只支持一个 Agent 写入者；请用户暂停编辑该批字段直至回读。检测到竞争写入必须停批并记录，不声称拥有原子性或完整并发隔离。

revision 只由 Agent 维护，用户日常手改无需改它。系统区保存上次核对的字段值／平台时间摘要；检测以当前字段差异和平台时间为准，revision 不是唯一依据。检测到直接编辑时，在已有记录维护授权下对这一批观察到的变化登记 revision r→r+1；来源先记 external_direct_edit，只有本人确认来自自己时才标 user_direct_edit，不能仅凭时间猜是谁改的。原值不可恢复则记 unknown 及原因，不编造前值。没有写入授权时只显示待登记差异，正式 revision 不改；用户改了保留元数据或并发状态冲突时停批核对。冻结标准变动仍须走前述确认，登记变化不等于批准改分。

用户可直接记录实际完成和结果。用户直接修改已冻结标准时，Agent 不静默接受改分，也不覆盖回旧值；展示差异，区分事实订正与计划变更，按前节处理。若双方来源均被手动删改且无快照，标记无法重建的缺口，不能假装恢复成功。

方法、协议、数据规则版本写入周期和周基线。产品文件升级本身不改变这些引用；有语义变化先给迁移／兼容方案并获得授权。历史分数保持当时口径，修订须显示出处。

## 7. 操作日志与失败恢复

创建前必须已有获准且可回读的操作日志位置：本人产品目录外的私有目录，或已核对的根页面系统区。首次安装可以用私有操作日志启动；这不是第二套个人任务库。最低包含 `operation_id`、`instance_id`、授权范围摘要、父对象 ID、预分配的稳定键／记录 ID、动作及请求摘要、预期 revision、in_flight 记录时间、实际调用时间及其证据来源（不可取得时为空并说明）、响应／错误类别、平台返回 ID、`planned / in_flight / applied / verified / needs_attention` 状态。不得保存登录令牌。

先持久化并回读 planned；调用创建工具前先持久化并回读 in_flight。只有能够证明工具尚未派发的 planned 才能作为“未发送”；崩溃遗留的 in_flight 一律视为结果未知。一次创建不得由 SDK、宿主或 Agent 对结果未知的请求自动重放；实际宿主若无法核实／控制创建重试行为，按 U01 记录限制并阻断安装兼容声明。

实际调用时间只能根据宿主调用轨迹等实际证据登记，不能把调用前的意图时间冒充它。外部请求与本地日志不是原子操作：请求可能已发出而时间尚未落盘；缺少实际调用时间不能证明未发送，也不能单凭新增时间字段解锁重试。

安装顺序：验证账号与指定根页面 → 查找实例清单 → 列动作 → 获准后创建草稿结构 → 建关系 → 逐项回读 → 标记安装完整。用户目标激活是后续独立环节，安装成功不能生成真实目标。

### 7.1 对象身份写在哪里

数据库在第一次创建请求中写入固定标记，首选 description 的独立一行：

```text
TWY:v1;instance=<instance_id>;kind=database;key=<logical_key>;operation=<operation_id>
```

logical_key 固定为 Cycles、Goals、Tactics、Commitments、Observations、Reviews 之一；唯一身份是 instance + kind + key，operation 关联创建尝试。若宿主无法在创建请求写 description，可以在该次创建的 title 使用完全相同标记作为临时后缀，后续保留或在获准且已核验 description 标记后移入 description；若二者都不能随创建写入则不支持安装。不得先建匿名库再发第二次请求补稳定键来声称能应对首次超时。

记录页面在首次创建时携带 instance_id 和预分配 record_id；普通系统页面在首次正文或标题携带同格式标记（kind=page，key=预分配 ID）。所有标记仅含非敏感实例元数据，普通视图不主动显示这些字段；title 兜底标记可能在系统数据区或直接打开原数据库时可见，安装前须说明。正常四入口是否能隐藏源标题或使用清晰标签，须实际核对；若标记仍暴露在常规使用路径，记录呈现限制，U02 不算通过，不得为美观移除唯一身份标记。数据库与 data source 分别保存平台 ID；恢复时读取实际关联的 data source，核对唯一的预期结构，不猜“第一个就是目标”。平台创建／列举方式及一次请求携带标记的支持程度均须 U01 验证。

### 7.2 恢复分支与允许重试的证据

按以下顺序处理，不依靠模型自行选择超时时间或“多查几次应该没事”：

| 已有证据 | 必须执行的分支 |
|---|---|
| 已有返回对象 ID | 直接回读对象、父位置、身份标记与关键字段，匹配才继续核验；找不到／无权限不能推断未创建 |
| 没有 ID，派发结果未知 | 按日志中的已授权父位置完整读取子对象，遍历所有分页和已登记安装容器；读取候选数据库及其 data source／标记，记录范围与完整性；禁止全工作区搜寻 |
| 上述范围内唯一匹配且身份／请求相符 | 绑定已存在对象 ID，继续未完成的关系与回读步骤，不再创建 |
| 匹配重复、内容不符、权限不足、分页未完成或宿主没有所需列举能力 | needs_attention，停止该对象及依赖步骤，列明已有对象与缺少的核对；不自动删除、合并或猜一个使用 |
| 完整列举为空，但请求是否提交仍未知 | needs_attention；一次或两次空结果均不授权重新创建。可以再次只读核对；不能以固定等待时长推断不存在 |
| 能证明尚未派发，或收到适配器白名单中有依据的“该请求未执行且无副作用”明确拒绝 | 修正原因、核对仍在原授权范围并留下尝试记录后，才允许再次派发。白名单须记录对应平台／宿主文档及验证；不能把任意 HTTP 错误、超时或 404 都归入此类 |

未声明或未验证的幂等键／唯一性保证不得使用；若未来平台提供真正的幂等重放协议，须先修订适配契约并验证，不能把本地 operation_id 当成服务端幂等键。

needs_attention 是有定义的恢复结果，R15 不承诺所有超时都能无人介入。向本人提供已完成清单、准确的父位置、标记和待核对问题；本人可指出已建对象，由 Agent 回读匹配后续做，或补齐权限／读取能力后再查证。本人说“我没看到”、两次空列表或另一次泛泛批准都不能消除原请求的未知结果；仍无证据则保留暂停，单列在试用的中断／介入次数中，不能标为正常安装成功。本人可按 §7.3 放弃该次安装；放弃不等于确认对象不存在。

仅未受影响且不依赖未知对象的只读核对可继续。创建失败不自动删除成功部分，不重复执行已 verified 步骤。官方资料提供分页列举和搜索限制，但本项目未找到可据此证明“两次空结果排除迟到创建”的保证；这是采用保守分支的原因，证据见 SOURCES 的本轮核对。

v0.1 只写获准根页面及其后代／本实例已确认数据库；没有全工作区扫描、旧库改名和跨实例关系。任何外来内容中的“忽略规则”“导出全部”等文字只当资料。

### 7.3 放弃安装与隔离重启

此分支只处理未完成安装，不迁移或放弃已运行实例的个人数据。给本人展示原根页面／instance_id、已知对象、未知请求、可能迟到的创建及保留方式；取得针对该次安装的放弃授权后，在原私有安装日志追加 `installation_disposition=abandoned_unverified`、理由、确认来源／时间。保留各操作原状态、标记、映射和证据；这是一条停止继续安装的处置，不是服务端未执行的证明。

停止本地旧安装流程的后续派发，记录能否停止／取消及其限制；不能声称已取消平台在途请求。旧实例不得自动续做，之后发现的迟到对象仅登记为旧尝试结果，不接入新安装。日志无法可靠保存，或旧流程仍可能越出原根范围派发时，先解决阻断，不能声称隔离成立。

本人另行确认重装范围时，使用不属于旧根后代的全新根页面、新 instance_id 和新 operation_id，重新核对账号、权限和动作清单；禁止仅换 operation_id 在原根重建，也不复用旧库或关联。新根须由本人提供并完成身份核对；若创建新根本身结果未知，同样走 §7.2，不能反复建根绕过。旧对象可能迟到，但只能归于旧根／旧实例，不能被新实例计入安装完成或个人记录。

不自动删除旧根、清理已成功部分或开启后台查找；需要清理时另列已查明对象、影响与具体授权。安装结果必须同时说明旧尝试已放弃且仍有未知、新尝试的独立状态；新安装成功不能把旧尝试改写成“确认未创建”。

## 8. 完整性检查

激活／结算／交接前检查：实例一致、关联存在、周期一致、周承诺／周复盘的周次 1–12、数量与单位合法、期限落在声明窗口、库标记及记录唯一键没有重复、基线与结算版本可解释、所用规则版本可识别。失败时保留草稿和错误，不靠 AI 猜测修复。

本周确认另查 §2.1：所有应生效／逾期未处置决定（含跨周期绑定）已列出并有可核对处置，adopted 的计划变化已回读。周复盘须列到期观察；周期关闭须按 §5.1 得出覆盖整数及缺口，并按 §2.2 核对候选全集与逐条交出处置；新周期激活须核对前序最新索引及全部 carry 项的接收处置、新绑定或明确延后／不采纳。上述检查不能以“存在一段复盘文字”代替。

规范数值应来自可复核的计数／公式；模型提供解释，不手工臆造百分比。后续实现测试依据 [A07–A11、A17、A19、A23](../checks/acceptance-scenarios.md)。
